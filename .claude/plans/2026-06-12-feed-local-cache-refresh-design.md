# Feed Local Cache + Top Refresh — Design

**Date:** 2026-06-12
**Status:** Approved by user (tab-session cache, per-post state restored, refresh prepends and keeps old posts)

## Problem

Feed posts are generated by Claude and never saved to the DB (only interaction
metadata is). `Feed.tsx` holds posts in component state, so navigating to the
dashboard or a lesson and back unmounts the component and throws the posts
away — the user pays tokens to regenerate a feed they already had. There is
also no way to ask for fresh posts at the top of the feed; new posts only
append at the bottom via the scroll sentinel.

## Goals

- Returning to `/feed` within the same tab session shows the previously
  generated posts (including page reloads) without a new generation call.
- Liked state, quiz answers, and viewed-tracking survive the round trip — no
  re-answerable quizzes, no duplicate interaction events.
- A refresh button at the top of the feed streams a new batch in **above**
  existing posts, in arrival order (Twitter-style "new posts on top").
- No server/DB storage. Cache lives in `sessionStorage` only.

## Non-goals

- Cross-session persistence (new tab or browser restart starts fresh).
- Caching across preference changes — saving preferences clears the cache, as
  it already resets the in-memory feed.
- Server-side caching or deduplication.

## Design

### 1. Cache module — `src/utils/feedCache.ts` (new)

Single owner of the storage shape. sessionStorage key: `bf:feed:v1`.

```ts
interface FeedPostState {
  liked: boolean;
  quizSelected: number | null;
  viewed: boolean;
}

interface FeedCache {
  posts: FeedPost[];
  postStates: Record<string, FeedPostState>; // keyed by client post id
  seenTags: string[];
}
```

- `loadFeedCache(): FeedCache | null` — returns null on missing key, JSON
  parse failure, or shape mismatch (treat any failure as a cache miss).
- `saveFeedCache(cache: FeedCache): void` — caps `posts` to the most recent
  60 before writing (drops `postStates` entries for evicted posts); catches
  and ignores quota/serialization errors — the feed still works, just
  uncached.
- `clearFeedCache(): void`.

Versioning is via the key suffix (`v1`); a future shape change bumps the key
and old entries simply miss.

### 2. `Feed.tsx` changes

- **Hydrate:** initialize `posts`, per-post state map, and `seenTagsRef` from
  `loadFeedCache()`. If cached posts exist, skip the initial `fetchBatch` and
  render immediately (no skeletons).
- **Write-through:** a `useEffect` over `[posts, postStates]` calls
  `saveFeedCache` (also persisting current `seenTags`).
- **Per-post state lifts up:** `Feed.tsx` owns
  `postStates: Record<string, FeedPostState>` and passes each card its entry
  plus an `onStateChange(postId, state)` callback (see §3).
- **`fetchBatch(placement: 'initial' | 'append' | 'prepend')`:** existing
  initial/append behavior unchanged. For `'prepend'`, posts stream in at the
  top in arrival order: track `insertedCount` local to the batch and insert
  each arriving post at index `insertedCount`, then increment — so the batch
  reads top-to-bottom in generation order, above all existing posts.
- **Refresh button:** `RefreshCw` icon button in the header next to the
  preferences button. On click: scroll to top, `fetchBatch('prepend')`.
  Disabled while any fetch is in flight (`inFlightRef`). A 429 sets the
  existing `rateLimited` state; existing posts stay visible.
- **Loading indicator for prepend:** one `PostSkeleton` above the post list
  while the prepend batch's first post is pending.
- **`handlePrefsSaved`:** additionally calls `clearFeedCache()` and resets
  `postStates` (it already clears posts/seenTags and regenerates).

### 3. `FeedPostCard.tsx` changes

- New optional props: `cachedState?: FeedPostState` and
  `onStateChange(postId: string, state: FeedPostState)`.
- `liked` / `selected` initialize from `cachedState` when present; every
  change reports up via `onStateChange`.
- The viewed-IntersectionObserver checks `cachedState?.viewed` — if already
  viewed, it neither re-records the `viewed` interaction nor re-observes.
  First-time views report `viewed: true` through `onStateChange` in addition
  to the existing `onInteraction` call.
- `likeRecordedRef` initializes true when restoring `liked: true`, so
  re-liking after restore doesn't double-count the analytics event.
- A restored quiz `selected` renders the answered state exactly as if just
  answered (existing render path; no new UI).

### 4. Data flow

```
mount → loadFeedCache → posts/postStates/seenTags hydrated → render
user interacts → card → onStateChange → Feed postStates → saveFeedCache
scroll bottom → fetchBatch('append')  → posts appended  → saveFeedCache
refresh click → fetchBatch('prepend') → posts prepended → saveFeedCache
prefs saved  → clearFeedCache + reset → fetchBatch('initial')
```

### 5. Error handling

- Cache read failure → silent fresh generation (current behavior).
- Cache write failure (quota) → caught in `saveFeedCache`, feed unaffected.
- Prepend fetch failure with existing posts → existing toast path ("Could not
  generate more posts"); cached posts remain.
- 429 on prepend → `rateLimited` banner; existing posts remain.

### 6. Testing

Manual verification (no test runner is configured for the frontend):

1. Generate feed → like a post, answer a quiz → navigate to dashboard →
   return: same posts, like and quiz answer intact, **no** `/claude/feed`
   call, no duplicate `viewed` events in the interactions request log.
2. Click refresh → skeleton at top → new posts appear above old, in order.
3. Reload the tab → feed restored. Open a new tab → fresh feed.
4. Save preferences → cache cleared, feed regenerates.
5. Scroll to bottom → append still works and is persisted.
